# RAG System Prompt 优化设想

当前阶段不实现回答评分、反馈入库、离线评测表或自动调 prompt。原因很简单：系统的检索质量、引用约束、知识库删除一致性和权限边界还在稳定中，过早引入评分闭环会让代码和数据模型承载不成熟的假设。

本文档只记录后续优化方向，避免把半成品实现污染代码仓库。

## 1. 目标

未来要优化的是 system prompt 对 RAG 回答行为的约束能力，包括：

- 无证据时稳定拒答，不补常识、不猜测企业内部规则。
- 有证据时优先引用证据原文，避免把多个文档内容混成未标注结论。
- 对流程类、错误码类、配置类问题采用不同回答结构。
- 对检索命中但证据不足的场景，明确告诉用户缺少哪类资料。

## 2. 可用信号

不依赖用户好评/差评，不设计评分表。后续可以从已有链路中提取这些非评分信号：

- `agent_trace`：路由、改写、检索、回答、校验节点的输入输出摘要。
- 检索元数据：Qdrant / Neo4j 命中数量、知识库过滤条件、引用文档标题。
- 回答状态：有证据回答、无证据拒答、模型调用失败、检索为空。
- 人工抽样记录：研发或知识库管理员在文档外部记录典型问题和期望回答风格。

这些信号只用于人工复盘和 prompt 设计，不在当前阶段自动入库为评分样本。

## 3. 后续方案

1. 人工抽样：从 Trace 面板挑选代表性会话，按“拒答是否准确、引用是否充分、结构是否清晰”做人工阅读，不在系统里打分。
2. 归纳 prompt 问题：把问题归成少量类型，例如“证据不足时回答过满”“步骤类答案不够结构化”“引用来源没有解释价值”。
3. 编写候选 prompt：只改 `ai-service/app/prompts/default.yaml`，并记录修改原因。
4. 小流量人工验证：用固定的知识库问题清单手工对比新旧回答，确认没有明显回归。
5. 发布前检查：确认无证据问题仍拒答、跨知识库问题不串数据、引用内容能支撑答案。

## 4. 暂不实现

以下内容当前不做：

- 用户点赞/点踩。
- 回答评分表。
- bad case 自动聚合。
- 离线评测表和评测运行脚本。
- LLM 自动改写 system prompt。
- 自动发布 prompt。

等 RAG 主链路稳定后，再评估是否引入独立的 prompt 实验模块。届时也应先设计隔离的数据表和人工审核流程，而不是把评分逻辑混入在线问答链路。
